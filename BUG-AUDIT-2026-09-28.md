## A. 产品缺陷 / A. Product defects

### A1. 训练模式：数字键 3 越界抛异常 / A1. Training mode: number key 3 out of range throws

**现象**：情境训练中，若当前题目只有 2 个选项，按数字键 `3` 会抛
`TypeError: Cannot read properties of undefined (reading 'key')`，按键无任何响应。

**Symptom**: In scenario training, if the current question has only 2 options, pressing number key `3` throws
`TypeError: Cannot read properties of undefined (reading 'key')`, and the key does nothing.

**根因**：`src/drill.js` 的数字键路由硬编码假定每题 3 个选项：

**Root cause**: `src/drill.js`'s number-key routing hard-codes the assumption of 3 options per question:

```js
if (n >= 1 && n <= 3 && !state.chosen) choose(current().options[n - 1].key);
//                                     ^^^^^^^^^^^^^^^^^^^^^^^ 未判空
```

**实证**（探针驱动真实浏览器，含对照组）：

**Empirical proof** (probe-driven real browser, with a control group):

```
当前题：river-bluffcatch，选项 2 个
  按 3 → chosen=null  attempts=0   pageerror: Cannot read properties of undefined (reading 'key')
  按 2 → chosen=call  attempts=1   无报错            ← 对照组
```

题库实测 **13 题中 1 题**（`river-bluffcatch`，河牌面对超池全下）只有「弃牌 / 跟注」2 个选项，
即约 **7.7%** 的出场概率会踩中。

Measured: **1 of 13 questions** in the question bank (`river-bluffcatch`, river facing an overbet all-in) has only the 2 options "fold / call",
so there is about a **7.7%** chance of hitting it.

**处置**：改为逐个判空。

**Fix**: changed to null-check each one.

```js
const s = current();
const opt = s && s.options[n - 1];
if (opt) choose(opt.key);
```

### A2. 切换设置后旧牌局未被终止 —— 幽灵数据污染画像（**最严重**） / A2. The old hand is not terminated after changing settings — ghost data pollutes the profile (**most severe**)

**现象**：在设置面板改动人数 / 盲注 / 起始筹码 / AI 速度并点「应用」后，**上一局并没有结束**，
它会继续在后台把这手牌打完。

**Symptom**: After changing player count / blinds / starting stack / AI speed in the settings panel and clicking "Apply", **the previous hand is not over**;
it keeps playing out this hand in the background.

**根因**：`src/main.js` 的 `createGame()` 直接 `new PK.Game(...)` 覆盖旧实例。而旧 Game 的
`_loop(gen)` 比较的是**它自己**的 `generation` —— 换新实例并不会让它停下。后果分两种：

**Root cause**: `src/main.js`'s `createGame()` directly does `new PK.Game(...)` overwriting the old instance. But the old Game's
`_loop(gen)` compares against **its own** `generation` — replacing the instance does not make it stop. Two kinds of consequences:

- 若旧局正轮到英雄行动 → 挂在 `_waitHero` 上（无害）；
- 若英雄已弃牌、剩下全是电脑 → **它会把整手打完**，并在 `_finalizeHand()` 里调用
  `PK.Profile.endHand()` / `observe()`。而 `PK.Profile` 是**单例**，
  于是往你的漏洞画像里塞进一整手**幽灵数据**，并被 `storage.js` 持久化
  （key `nlhe-trainer-v1` 的 `profile` 字段）—— 之后 AI 就照着这份脏画像针对你。

- If the old hand is at the hero's turn → it hangs on `_waitHero` (harmless);
- If the hero has folded and the rest are all computers → **it plays out the whole hand** and calls
  `PK.Profile.endHand()` / `observe()` in `_finalizeHand()`. And `PK.Profile` is a **singleton**,
  so it stuffs a whole hand of **ghost data** into your leak profile, which is persisted by `storage.js`
  (the `profile` field of key `nlhe-trainer-v1`) — after which the AI targets you based on this dirty profile.

同一处还发现：`engine.js` 的 `resetAll()`（自增 generation + resolve 挂起等待，正是为终止而写）
**在全项目零调用** —— 修好了却没接线。

The same place also revealed: `engine.js`'s `resetAll()` (increments generation + resolves the pending wait, written exactly for termination)
**is called nowhere in the whole project** — it was fixed but never wired up.

**处置**：`createGame()` 开头先终止旧实例。

**Fix**: `createGame()` first terminates the old instance at the start.

```js
if (game && typeof game.resetAll === 'function') game.resetAll();
```

**验证**：新增 `test/check-settings-apply.js`（**8 项**，真实浏览器）。
判据用**终止不变式**而非后果：`stage` 全项目只有三处赋值 —— 构造 / `resetAll()` 给 `'idle'`、
`newHand()` 给 `'betting'`、结算给 `'over'`，所以旧实例读到 `'idle'` **只能**是被显式终止。

**Verification**: new `test/check-settings-apply.js` (**8 items**, real browser).
The criterion uses a **termination invariant** rather than consequences: `stage` is assigned in only three places project-wide — the constructor / `resetAll()` giving `'idle'`,
`newHand()` giving `'betting'`, and settlement giving `'over'`, so an old instance reading `'idle'` **can only** mean it was explicitly terminated.

**正反对照**（判别力证据）：

**Positive/negative control** (evidence of discriminating power):

| 条件 / Condition | 结果 / Result |
| --- | --- |
| 含修复 / With the fix | **8/8 全绿**（连跑 2 次） / **8/8 green** (run twice) |
| 摘掉修复 / Fix removed | **4 项转红**（旧实例停在 `stage=betting, toAct=4`，还在跑） / **4 items turn red** (old instance stuck at `stage=betting, toAct=4`, still running) |

> 第一版断言曾写成"旧实例 `recents` 不再增长"，两种条件下都通过 —— 属**恒真断言**，
> 已按铁律删除并换成不变式判据。
>
> The first version of the assertion was written as "the old instance's `recents` stops growing", which passed under both conditions — a **tautological assertion**,
> removed per the iron rule and replaced with the invariant criterion.

## B. 测试侧缺陷 / B. Test-side defects

### B1. `features.js`：把概率命题写成断言 / B1. `features.js`: writing a probabilistic proposition as an assertion

`ok('渲染出选项按钮', drill0.opts >= 3)` —— 训练面板首题是**随机洗牌**抽出的，
首题恰好是那道 2 选项题的概率为 **1/13 = 7.69%**，此时断言必然假失败。

`ok('渲染出选项按钮', drill0.opts >= 3)` — the training panel's first question is drawn by **random shuffle**,
so the chance that the first question is exactly that 2-option one is **1/13 = 7.69%**, at which point the assertion necessarily false-fails.

**处置**：改为断言"与该项自己的数据一致"，而非与全局常量 3 比。

**Fix**: changed to assert "consistent with this item's own data", rather than comparing against the global constant 3.

### B2. `check-profile.js` 组 8：零容差断言 + 统计功效不足 / B2. `check-profile.js` group 8: zero-tolerance assertion + insufficient statistical power

**现象**：批跑时偶发红一次，单独跑 40 次却全过（0.987⁴⁰ ≈ 60%，符合预期）。

**Symptom**: In batch runs it occasionally goes red once, yet run alone 40 times it passes all (0.987⁴⁰ ≈ 60%, as expected).

**量化**（新建 `test/probe-profile-stats.js`，逐条打印假失败率与 **σ 余量**）：

**Quantification** (new `test/probe-profile-stats.js` prints the false-failure rate and **σ margin** per item):

| 场景 / Scenario | 断言 / Assertion | 假失败率 / False-failure rate | 余量 / Margin |
| --- | --- | --- | --- |
| 组 8 `hands=500` / Group 8 `hands=500` | `warnings.length === 0` | **0.367%**（22/6000） | `riverCall` 2.9σ / `foldTo3Bet` 3.1σ |
| 组 8 `hands=1600` / Group 8 `hands=1600` | 同上 / same | **0.000%**（0/6000） | **4.3σ / 4.9σ** |
| 其余 29 条 / The other 29 items | — | 0.00% | 全部 ≥ 4σ / all ≥ 4σ |

**根因**：组 8 是**零容差**断言（标准玩家不该被报出任何警告级漏洞），却建立在随机合成样本上。
标准玩家 `riverCall` 真值 0.417 / warn 线 0.56，`foldTo3Bet` 真值 0.520 / warn 线 0.68 ——
样本比例偶尔越线就被判成漏洞。

**Root cause**: Group 8 is a **zero-tolerance** assertion (a standard player should not be reported with any warning-level leak), yet it is built on random synthetic samples.
The standard player's `riverCall` true value is 0.417 / warn line 0.56, and `foldTo3Bet` true value 0.520 / warn line 0.68 —
occasionally the sample ratio crosses the line and gets judged as a leak.

**处置**：按铁律"**加样本，不放宽阈值**"，组 8 样本 **500 → 1600 手**（σ ∝ 1/√n），
复跑 **20/20 全过**。

**Fix**: per the iron rule "**add samples, do not relax the threshold**", group 8 samples **500 → 1600 hands** (σ ∝ 1/√n),
rerun **20/20 all pass**.

> **途中踩的坑**：300 次采样把 0.367% 读成了 **1.00%**（3/300）。
> 稀有事件的估计误差极大 —— **定标必须用大样本**，小样本反复"确认"只会得到互相矛盾的读数。
>
> **A pitfall hit along the way**: 300 samples read 0.367% as **1.00%** (3/300).
> The estimation error for rare events is huge — **calibration must use large samples**; repeatedly "confirming" with small samples only yields contradictory readings.

**配套重构**：把合成器与场景预设收敛到 `test/synth-player.js`（**唯一配置源**）。
起因是探针里另抄了一份配置，改了验收脚本的 `hands` 却忘了同步，
导致探针拿旧配置算出"仍然脆弱"的**错误结论**。**配置即被测对象的一部分，分叉了探针就失去证明力。**

**Supporting refactor**: the synthesizer and scenario presets were consolidated into `test/synth-player.js` (**the single configuration source**).
This started because the probe had copied a second configuration; when the validation script's `hands` was changed the copy was not synced,
so the probe computed a **wrong conclusion** of "still fragile" using the old config. **Configuration is part of the object under test; once forked, the probe loses its proving power.**

## C. 环境陷阱 / C. Environment pitfall

### C1. 窗口被系统判为"不可见"时，Chrome 挂起整个全屏状态机 / C1. When the window is judged "invisible" by the system, Chrome suspends the whole fullscreen state machine

**现象**：`verify-render.mjs` 5 项全屏断言里 **2 项确定性红**：
`fullscreenElement` 已非空（全屏确实进去了），但按钮状态不同步、`exitFullscreen()` 也无效。

**Symptom**: Of `verify-render.mjs`'s 5 fullscreen assertions, **2 are deterministically red**:
`fullscreenElement` is already non-null (fullscreen really did enter), but the button state is out of sync and `exitFullscreen()` has no effect either.

**取证**：新建 `desktop/probe-fullscreen.mjs`，装"黑匣子"包住 `requestFullscreen`
记录其 resolve/reject，并记录两种 `fullscreenchange` 事件。一眼看到根因：

**Evidence collection**: new `desktop/probe-fullscreen.mjs` installs a "black box" around `requestFullscreen`
recording its resolve/reject and logging both `fullscreenchange` events. The root cause is visible at a glance:

```
document.hasFocus()       : true
document.visibilityState  : hidden          ← ★
事件轴：install → requestFullscreen → resolve → （此后**再无任何 change 事件**）
```

**机制**：Chrome 在 Windows 上默认开启原生窗口遮挡判定（`CalculateNativeWinOcclusion`）。
窗口被系统判为不可见时页面进入 `hidden`，Chrome 随即**挂起整个全屏状态机**：
`fullscreenElement` 与 `(display-mode: fullscreen)` 都乐观置真，但
`fullscreenchange` / `webkitfullscreenchange` **永不触发**，`exitFullscreen()` 同样无效（实测卡住 3.5s）。

**Mechanism**: On Windows, Chrome enables native window-occlusion detection by default (`CalculateNativeWinOcclusion`).
When the window is judged invisible, the page enters `hidden`, and Chrome then **suspends the entire fullscreen state machine**:
both `fullscreenElement` and `(display-mode: fullscreen)` are optimistically set true, but
`fullscreenchange` / `webkitfullscreenchange` **never fire**, and `exitFullscreen()` is likewise ineffective (measured: stuck for 3.5s).

**对照实验**（同一份源码）：

**Control experiment** (same source):

| 启动参数 / Launch arg | `visibilityState` | 事件轴 / Event timeline | 按钮 `aria-pressed` / Button `aria-pressed` | 退出 / Exit |
| --- | --- | --- | --- | --- |
| 不加 / not added | `hidden` | 只有 resolve，**无 change** / only resolve, **no change** | 始终 `false` / always `false` | 无效 / no effect |
| `--disable-features=CalculateNativeWinOcclusion` | `visible` | `change(true)` 正常触发 / `change(true)` fires normally | `true` | 生效 / effective |

`Page.bringToFront` **治不了**（实测仍 `hidden`）。

`Page.bringToFront` **does not cure it** (measured: still `hidden`).

**处置**（两件都做）：
1. 启动参数加 `--disable-features=CalculateNativeWinOcclusion`；
2. 仍**显式断言前置** `visibilityState === 'visible'`；不满足时把这 5 项标成 **`⊘ 作废`**
   —— 新增 `invalidate()`，既不算通过也不算失败，整轮 `ok=false` 并在汇总写明
   "本轮作废，不是产品缺陷"。`verify-entry.mjs` 同步支持 `⊘`。

**Handling** (both required):
1. Add the launch arg `--disable-features=CalculateNativeWinOcclusion`;
2. Still **explicitly assert the precondition** `visibilityState === 'visible'`; when unmet, mark these 5 items as **`⊘ invalidated`**
   — a new `invalidate()` counts as neither pass nor fail, sets the whole round's `ok=false`, and states in the summary
   "this round is invalidated, not a product defect". `verify-entry.mjs` supports `⊘` in sync.

**为什么不做成"判红"**：判红会让人以为产品坏了（本项目已被误导过一次）；
算通过则等于把"没测"伪装成"测过了"（恒真断言，等于没写）。两者都不可接受。

**Why not make it "red"**: red would make people think the product is broken (this project was misled once);
counting it as pass would disguise "not tested" as "tested" (a tautological assertion, i.e. not written at all). Both are unacceptable.

> **附带教训**：做反向对照时只摘掉 `fullscreenchange` 一条监听，断言**照样绿** ——
> 按钮同步有**三条冗余路径**（`fullscreenchange`、`webkitfullscreenchange`、
> `display-mode` 媒体查询的 `change`）。**把三条全摘掉才转红**。
> 对照实验必须穷尽所有能产生该效果的路径，否则"没变红"只说明对照无效。
>
> **Side lesson**: when doing the reverse control and removing only the `fullscreenchange` listener, the assertion **stayed green** —
> button sync has **three redundant paths** (`fullscreenchange`, `webkitfullscreenchange`,
> and the `change` of the `display-mode` media query). **Only removing all three turns it red.**
> A control experiment must exhaust every path that can produce the effect; otherwise "it didn't turn red" only means the control is invalid.
